# Emoji 簇级后备修复与验收（2026-09-08）

后续修正：[混排基线对齐](emoji-baseline-alignment-2026-09-08.md)处理片段顶部补位导致的 Emoji 偏低。本页保留整簇后备阶段的测量记录。

## 问题与原因

editor 种子文本中的 `👩🏽‍💻` 是一个扩展字素，由四个码点组成，占 15 个 UTF-8 字节。此前看到的“头像＋操作电脑”是同一字素被错误拆图，不是两个独立表情。选区把它作为整体是正确行为。

修复前直接调用原版 SDL_ttf 3.2.2 即可复现：UI 主字体缺少组合字形时，其后备分段在字符串末尾输出重复头像；追加内容后，先前组合的第二张图才改变。TextArea 复制、粘贴的数据始终为原来的 15 字节；错误发生在缺字后的 shaping，而非剪贴板、文本存储或图集键。

## 实现

- CangjieSDL 按完整扩展字素选择可以承载整个 Emoji 的字体；相邻同字体片段合并后再 shaping，避免逐个取整导致累计宽度误差。没有可用整簇字体时保留原生结果。
- 通过官方 `TTF_CreateText`、`TTF_UpdateText` 及公开布局数据验证字形来源；复用已打开、被会话固定的字体。没有改动 SDL_ttf、引入 `native/` 或新增启动时目录枚举。
- 修正后的字形、源字节偏移与字体片段同时供绘制、度量、换行适配和命中使用。普通文字保留直接测量快路径；Emoji 适配宽度时不会截断字素，也不会将剩余宽度 0 传给原生 API 的“不限宽”参数。
- GUI 和 SDL 共用 Unicode 17 的字素状态机及数据，避免两份运行时表。SDK 新增纯函数 `sdl.text.graphemeByteBoundaries` 和 `graphemeRuneBoundaries`，不初始化字体或 SDL。
- VS16 优先选择已注册的彩色候选，VS15 保留文本呈现路径；实际组合是否有完整图案仍取决于字体。例如部分字体只提供区域字母，没有国旗组合字形。

像素对照还暴露了两处边界问题，已同时修正：

1. 彩色字形的实际 bearing 可能令墨迹超出布局顶部，斜体也可能伸到左侧。Surface 现在保留这些像素，并携带绘制原点偏移；逻辑尺寸、旋转中心不随补边改变。
2. 完全包含的嵌套矩形裁剪重新计算高度会产生浮点舍入误差，在 4.5 倍实际栅格比例下扩大一行像素。矩形交集现在直接保留被包含矩形的精确尺寸，并有独立回归。

## 资源控制

普通 Latin／CJK 文字先用低成本筛选跳过 Emoji 路径。候选字体来自现有后备链，不额外打开整套字体。单次布局的字体选择缓存最多 128 项、64 KiB，布局完成即释放；测量会话保留字素边界和最近一个范围布局，关闭时释放。Surface 临时字形图像及墨迹边界继续受 8 MiB 预算约束，文本 Surface 上限仍为 16M 像素。

复用修复前冻结的探针可执行文件，以及相同探针源码在修复后的构建；8 种工作负载各做 6 组交替顺序对照，共 96 个独立进程。测试时不并行编译或运行其它验收。以下为各进程结果的中位数；内存是进程私有提交量，包含仓颉堆与原生分配，不是显存。首次启动计时从进程创建到完整首帧显示后的下一轮事件处理，不代表文件系统冷缓存启动。

| 启动场景 | 私有内存，修复前 → 后 | 启动耗时，修复前 → 后 |
| --- | ---: | ---: |
| 普通文字 | 57.83 → 57.97 MiB | 172.16 → 172.91 ms |
| 含 Emoji | 66.36 → 66.52 MiB | 177.30 → 182.21 ms |

含 Emoji 相对普通启动的额外内存仍约 8.55 MiB；本次修复没有再次引入先前约 16 MiB 的整套字体加载。启动耗时的数毫秒差异同时受到进程调度影响，不将小幅差异解释为稳定的加速或退化。

字体工作负载各运行 180 帧，暖帧跳过前 32 帧。编辑器场景为 100 行普通中英文软换行首排及 202 次滚动布局，用于检查普通文本回归；固定内容的暖帧包括缓存命中，不代表每帧新输入长文本的成本。

| 工作负载 | 最终私有内存，前 → 后 | 暖帧中位数，前 → 后 | 暖帧 P95，前 → 后 |
| --- | ---: | ---: | ---: |
| 普通文字 | 58.59 → 58.47 MiB | 0.225 → 0.244 ms | 0.591 → 0.598 ms |
| 重复 Emoji 混排 | 66.28 → 66.52 MiB | 0.203 → 0.226 ms | 0.395 → 0.462 ms |
| 斜体 Emoji 混排 | 65.50 → 65.74 MiB | 0.261 → 0.251 ms | 0.465 → 0.430 ms |
| 32 个字体配置轮换 | 108.29 → 114.12 MiB | 1.013 → 1.092 ms | 1.843 → 2.022 ms |
| 24 个字号轮换 | 173.70 → 157.26 MiB | 5.188 → 5.123 ms | 6.336 → 11.022 ms |
| 100 行编辑器软换行 | 102.33 → 102.67 MiB | 0.083 → 0.084 ms | 0.178 → 0.236 ms |

普通固定字号的成本基本稳定；32 配置轮换增加约 5.83 MiB 和 0.079 ms 暖帧耗时。**24 字号轮换的尾延迟确有增加**：P95 的六进程范围由 6.15～6.59 ms 变为 10.63～11.31 ms，不能归为单次噪声。该场景每帧跨越已有彩色字体预算，新增整簇布局也增加冷路径工作；180 帧进程总 CPU 中位数由 1164.06 变为 1257.81 ms。尚未将额外 CPU 精确拆分到 shaping、分配和 GC，保留为后续性能项。

24 字号场景的峰值私有提交量为 180.72 → 181.19 MiB，基本不变；最终内存变小不足以证明峰值优化，可能与堆回收时点有关。本轮保留有界缓存和正确的组合字形，没有通过提高缓存预算掩盖尾延迟。详细分布、MAD、进程原始标记、字体及二进制摘要保存在[资源测量数据](assets/emoji-cluster-resources-2026-09-08.json)。

## 验证范围

本机 Windows、仓颉 1.0.5、原版 SDL_ttf 3.2.2。字体组合验证使用已安装的 Microsoft YaHei 与 Segoe UI Emoji。SDL3_ttf.dll SHA-256：`9A3DEFA81CFB71A48256333F1A015EE72A9B7D82311891CDC87AFCB9F23EC5A9`。

- CangjieSDL／CangjieGUI：235／954 项测试通过。两仓库各运行 766 组 Unicode 17 官方字素边界样本。
- 30 组 Emoji 像素对照：10 种组合 × 18／32／48 pt，比较默认后备结果与 Emoji 字体作为主字体的完整 shaping，非透明图像逐 RGBA 像素一致。
- 连续 1～4 次重复、范围度量、换行边界、鼠标命中、复制／剪切／撤销／重做；包括可独立选择的 `👩🏽 💻` 与不可拆开的 `👩🏽‍💻`。
- 原生窗口端到端：14 场景 × 3 轮全部通过；新增 `emoji-paste` 在 1×／2× 超采样下检查交互和截图，原有启动、编辑样式、滚动裁剪、失败恢复及增量绘制回归继续通过。
- 新增 Emoji 截图参照允许最多一行物理像素的整体纵向平移，以容纳分数 DPI 下两种主字体各自的基线量化；所有 RGB 像素必须完全匹配，不容许色差或横向偏移。原有增量／完整绘制差异为 0。
- 两仓库严格 L2 相对修复前基线新增 0；完整门禁中的既有 cjlint／cjfmt 告警仍记录在日志，未宣称全仓告警清零。
- editor／fonts／richtext：测试及真实窗口截图 6 项门禁全部通过，更新示例截图；GUI／SDL 开发工具测试 93／14 项通过。
- GUI／SDL 文档检查覆盖 251／154 个 Markdown 文件，140／88 个文档程序片段编译通过。

长期的复杂脚本上下文 shaping、段落 bidi、Linux／macOS 实机与不同字体版本验收仍在待办中；本轮不把 Windows 的 Emoji 修复等同于全部文本国际化能力已完成。
