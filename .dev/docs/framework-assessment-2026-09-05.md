**CUI 框架完备性评测与迭代建议 · 2026-09-05**

当前 CUI 已形成有实际应用价值的声明式桌面 GUI 框架：状态、增量构建、布局、事件、渲染、资源生命周期和测试基础比较扎实，能够支撑 Windows 上的中小型业务工具、设置页、看板和轻量工作台。

相对于“可长期维护、面向多平台最终用户的通用桌面框架”，当前仍有明显距离。主要短板集中在静止界面的效率、文本编辑语义、控件无障碍覆盖、桌面窗口协议、运行时主题、复杂数据控件，以及可复现发布。这些问题比继续增加装饰性控件更值得优先投入。

建议下一阶段以“现有能力在真实应用中可靠成立”为主线，保留已经验证的增量内核，通过可复现反例补齐外围契约。此前的“下一代重构完成”是一个限定范围的架构验收结论，不能直接解释为整个 GUI 产品栈完备。

**完备程度矩阵**

**值得保留和继续投入的优点**

1. **内核围绕一致性设计。** 自动组合、稳定代数句柄、构建事务、提交后的生命周期效果，以及布局/事件/语义片段一起提交，针对的是 GUI 中难复现的状态错配问题。对应实现和失败测试已经存在，不是只在架构文档中提出设想。可参见 [automatic_composition.cj](../../src/core/automatic_composition.cj)、[element_layout.cj](../../src/core/element_layout.cj)、[transaction_failure_test.cj](../../src/testing/transaction_failure_test.cj)。
2. **小应用与复杂应用有渐进使用路径。** 简单页面可以直接组合 State 和控件；共享动作和跨模块业务可以逐步引入 Store、Reducer 和 EffectStore。业务状态与外部效果的边界较清楚，有助于独立测试。后续应保护这条渐进路径，避免把高级状态工具变成入门前置条件。
3. **性能工作有较好的证据意识。** 阶段计数、规模测试、同进程配对、样本稳定性、源码与机器环境摘要、基线候选晋升，以及增量/全量像素对照，比只报告平均 FPS 更有意义。此前拒绝未达到端到端门槛的 SDL_GPU 生产迁移，是合理的技术取舍。参见[架构决策](phase3-architecture-decision.md)。
4. **专用虚拟列表已经深入到数据身份和几何一致性。** 自测量行高、结构 revision、滚动锚点和 index/key 定位解决了真实列表会遇到的问题。应该将这些已验证原则扩展到表格、树和编辑器数据层。
5. **文档和示例是可继续建设的资产。** 指南覆盖开发任务，API 与源码有自动对照，48 个示例提供了公开接口使用样本。本次抽查的工作台、设置页和表格具有一致的排版、颜色、圆角和表面层次，可作为设计系统的起点。
6. **资源与线程边界有明确约束。** UI 线程投递、逆序资源清理、有预算的缓存、渲染资源代数和无障碍消费者故障隔离，都有助于保持长生命周期应用的可维护性。但还需要用整机内存和长时场景补充当前局部证据。

**优先问题与改进方向**

下文 P1 表示建议下一轮优先处理，P2 表示后续能力迭代，P3 表示由目标应用需求驱动。P1 不等于所有应用都会立即失败；它表示影响较广、反例明确或会限制发布承诺。

**F1 · P1 · 静止 Table 会不断使界面失效，已实测复现。**

[table.cj](../../src/controls/table.cj) 第 168 行在每次 `draw` 中无条件执行 `scrollOffset.value = clampScrollOffset(...)`。而 [state.cj](../../src/core/state.cj) 的默认 State 在每次赋值时都会推进 revision 并使调度器失效，包括等值赋值。DesktopApp 明确将 draw 阶段产生的写入留到下一帧处理，因此静止表格可以持续触发重绘。

探针在同机使用两个 300×180、开启 vsync 的真实窗口，只安排一次 1 秒后的关闭截止时间，没有 Frame 订阅或连续动画。普通 Label 对照观察到 2 次绘制回调，只有一行数据的静止 Table 观察到 122 次，实际观察时长分别为 1000/1006 ms。这个数字是当前机器的反例，不是跨机器性能基准；持续失效的源码原因是确定的。

建议只在 clamped offset 真正变化时写入，或为私有数值状态使用明确等价策略，并检查其它内置控件的绘制副作用。不要为了修正一个控件而改变默认 State 的公开赋值契约。

验收应增加“空闲”维度：无输入、无动画、无焦点闪烁时，各静态控件在启动/暴露事件处理完后停止自发提交；滚动到底、重复选择、空输入也不制造持续失效。同时验证滚动夹紧和选择自动可见功能没有退化。现有每帧性能基准不足以发现“根本不该产生这些帧”的问题。

**F2 · P1 · 文本显示与编辑的字符边界不一致，已实测复现。**

[text_edit_utf8.cj](../../src/text/text_edit_utf8.cj) 第 47/62 行只跳过 UTF-8 continuation byte，因此保证的是码点边界。[text_edit_state.cj](../../src/text/text_edit_state.cj) 的左右移动和前向删除直接使用这些边界。显示侧已经有 [text_grapheme_break.cj](../../src/core/text_grapheme_break.cj) 的字符簇处理，编辑侧未复用相同语义。

| 输入，均从字符串开头操作 | 总 UTF-8 字节数 | 按一次右键后的偏移 | 一次前向 Delete 后剩余字节 |
|---|---:|---:|---:|
| `e` + U+0301 组合重音 | 3 | 1 | 2，只剩组合重音 |
| 家庭 emoji `👨‍👩‍👧‍👦` | 25 | 4 | 21，序列被拆开 |
| 国旗 `🇨🇳` | 8 | 4 | 4，只剩一个区域指示符 |

建议建立统一的文本边界与位置映射服务，使光标、选区、前向删除、点击命中和渲染使用一致的默认字符簇边界。公开 byte offset 可以继续保留，但外部传入位置应有明确归一化规则。Backspace 可以根据平台约定有不同粒度，必须显式定义并测试，不能把任何码点级删除一概判为违反 Unicode。[UAX #29](https://www.unicode.org/reports/tr29/) 对字符簇、编辑操作和允许定制的边界有具体说明。

验收至少覆盖组合附加符、ZWJ emoji、肤色、旗帜、CRLF、CJK 标点、混合语言和 IME 组合提交；将已声明支持的 Unicode 版本及对应分段测试数据纳入门禁。

**F3 · P1 · 无障碍基础设施领先于控件覆盖，已实测复现。**

独立 WidgetTestHost 分别构建单个控件后的默认语义节点数如下。探针没有额外调用 `.semantics(...)`。

| 控件 | 节点数 |
|---|---:|
| Button / Checkbox / TextField | 各 1 |
| Switch / Slider / TextArea / Table / TreeView | 各 0 |

这说明“语义树和 UIA 桥已经存在”尚不能保证常用控件可以被辅助技术发现和操作。手写语义包装可改善单个应用，但不能代替框架内置控件的默认角色、状态、子项结构和动作。

平台上，[desktop_accessibility.cj](../../src/desktop/desktop_accessibility.cj) 第 155 行之后明确在非 Windows 返回 `None`。Windows [cui_uia.cpp](../../platform/windows/accessibility/uia/cui_uia.cpp) 的 `GetPatternProvider` 目前覆盖 Invoke、Value 和 Toggle，未提供文本范围、选择、展开折叠、表格/网格及范围值等完整模式。特别是编辑文本的读取与范围导航不能仅靠 Value 代替，参见 [Microsoft UIA 文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingvalue)。

建议先建立“每种可交互控件必须具备哪些语义”的矩阵，补齐常用控件默认语义及动作，再扩展 Windows Pattern；Linux AT-SPI 与 macOS 原生可访问性适配按平台发布计划推进。原生桥失败和桥缺失应当是可查询的能力状态。

验收既要有逐控件语义测试，也要有独立 UIA 客户端和 Narrator 等真实使用流程；非 Windows 的相应平台验收通过前，文档应明确限定原生无障碍支持范围。

**F4 · P1 · Modal 有 Tab 圈定，但焦点进入与恢复协议不完整，已实测复现。**

探针先聚焦 `opener` 按钮，再打开带有 `inside` 按钮的 Modal。打开后焦点仍为 `opener`；按 Tab 后变为 `inside`；按 Escape 关闭后焦点为空。对应实现位于 [modal.cj](../../src/controls/modal.cj) 第 96、158 行，现有[故障排查文档](../../docs/guide/troubleshooting/common-problems.md)也明确没有 opener/restore-target 参数。

建议增加明确的初始焦点、打开者记录、关闭后恢复与打开者已卸载时的后备目标，并统一 Escape、遮罩、按钮和程序关闭的路径。危险或必须完成的对话框还需要可配置的关闭策略。可参考 [WAI 对话框交互模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)中的焦点进入与恢复原则；这是交互设计参考，并非给桌面程序强加 Web 属性。

验收覆盖嵌套 Modal/ComboBox、打开者消失、禁用项、零可聚焦项和多种关闭方式。对话框焦点正确与原生 Dialog 语义应一起完成。

**F5 · P1 · 缺少面向文档应用的关闭确认契约，源码确认。**

[desktop_app.cj](../../src/desktop/desktop_app.cj) 第 499 行的事件路由先调用 `handleWindowEvent`；第 544 行之后将 Quit 和 WindowCloseRequested 直接转换为 `ctx.requestClose()`，随后返回，不进入普通 Widget 事件链。当前公开 DesktopApp 接口没有关闭否决或异步确认钩子。

这会限制“内容有未保存修改时弹出保存/放弃/取消”的应用流程。应用可以做自动保存或另建宿主，但不能在现有常规 CUI 窗口事件链中自然实现这个确认。

建议把“请求关闭”和“完成关闭”区分为宿主生命周期中的两个阶段，支持允许、取消和异步等待确认；并验证后台任务完成、重复关闭请求、保存失败和资源清理只发生一次。该能力应优先于多窗口扩展。

**F6 · P2 · 表格和树的惰性程度不及 Lazy 系列，源码与计数确认。**

[Table.of](../../src/controls/table.cj) 第 137 行之后会为全部行、全部列建立字符串矩阵，成本为 O(N×C)。独立探针对 10,000 行、1 列进行一次构造，value 提取器被调用 10,000 次。排序路径的 `displayOrder` 在每次执行时还扫描完整排序列校验缓存；[TreeView](../../src/controls/tree_view.cj) 第 121 行在构造时展开所有当前展开的节点。

这些成本发生在相应构造或绘制路径被执行时，不能笼统说成所有干净帧都重建全量数据。自动组合缓存可以跳过干净构建，但不会把真正执行的数据转换自动改成视口级复杂度。

Table 的 custom cell 当前是绘制回调，源码说明它不接收单元格事件；选择保存为原始行索引，能跟随当前数据的排序，但不能天然保证外部插入/删除/重排后的业务身份。列宽固定、单选、字符串显示及排序模型，也限制了复杂表格应用。

建议按目标应用增加带稳定行 key 和变更通知的数据接口、按可见范围取值、可复用排序/过滤结果；随后支持列调整、横向滚动、单元格编辑和多选。树则优先支持按需加载子节点和增量展开索引。验收应统计取值/构建/测量次数，覆盖 10k/100k 行、局部更新、排序、插入、删除和选择保持，而非只看绘制多少行。

**F7 · P2 · 主题、字号与国际化尚未形成完整运行时环境。**

[UiContext](../../src/core/ui_context.cj) 的主题是 `public let theme`，[主题指南](../../docs/guide/how-to/theme-an-app.md)明确当前不能在运行中热切换主题。settings 示例的主题和字号选项主要改变模型与摘要，不能用这些控件的存在证明真实外观会同步改变；本次看到的“深色已选、整体仍为浅色”也与该实现相符。

[DatePicker](../../src/controls/date_picker.cj) 第 18 行的星期标签固定为中文，未见统一的应用 locale/文本方向接口。一些内置控件直接使用固定的 FontSizes 和行高，不能仅凭 `.fp` 的存在推断所有控件都能完整响应字体缩放。例如 Button 测量会缩放文字宽度，但高度仍为固定控制高度，见 [basic_widgets.cj](../../src/core/basic_widgets.cj) 第 100 行。

建议将主题、字号、密度、locale、文本方向和系统偏好纳入可观察环境，以现有环境代数触发恰当缓存失效。先交付运行时浅/深切换、125%/150%/200% 字号可用性和紧凑密度；RTL 与日期数字格式按目标市场推进。保留当前默认视觉作为兼容基线。

**F8 · P2 · 编辑器和媒体更接近基础组件，适用边界需要清晰。**

TextArea 基于完整 String 和按换行符分割的缓存，编辑会重新产生文本并刷新行缓存；[UndoHistory](../../src/text/text_history.cj)最多保存 300 个完整文本快照，限制了条目数，但没有文档字节预算。大文档和长时编辑仍可能造成明显分配及内存压力。本次没有测出其最大可用文档量，不能从短文本测试推导专业编辑器能力。

尚未见完整的软换行编辑、可视列导航、双向文本位置映射、密码输入、统一表单错误/验证协议等公开能力。应先改善常规表单与中等文本量编辑，只有存在明确长文应用目标时才引入分块文本结构、增量行索引和差量撤销。

ImageView 已有缓存预算、失效接口和错误计数，但首次加载位于绘制路径；缺图或解码失败默认不绘制内容，见 [image_view.cj](../../src/media/image_view.cj) 与 [texture_cache.cj](../../src/media/texture_cache.cj)。建议按需补充异步加载、加载中/失败占位和错误回调。视频、WebView、完整图表、打印/PDF 输出等应视为可选扩展方向，不应作为每个轻量 GUI 核心必须内建的功能。

**F9 · P1 · 发布和质量门禁的可复现性有缺口，源码确认。**

仓库 HEAD 的 SDL git 依赖没有固定 revision；当前本机使用旁路路径依赖；[跨平台工作流](../../.github/workflows/cross-platform-qualification.yml)默认检出配套 CangjieSDL 的 `main`；`cjpm.lock` 被忽略。这意味着同一个 GUI 提交在不同时间可能配到不同 SDL 源码。已有工具链和 SDL 原生制品的哈希固定是优点，但并没有覆盖这条配套源码依赖。

另外，[.gitignore](../../.gitignore)忽略 `.cjcheck.json`、`.cjcheck-baseline.json`、格式配置和 `.agents/`；本机这些配置及检查器存在，但当前仓库不跟踪它们。现有 GitHub 工作流也没有执行本机这条严格 L2 基线门禁。因此，本次“新增 0”是本机有效结果，尚不能代表其他贡献者和 CI 自动执行同样的标准。

建议发布时固定 GUI、SDL 和原生桥的组合版本，保存来源摘要；把项目级规则、可审查基线、格式配置及检查器获取版本纳入可复现流程，并在 CI 执行。SDK/SDL 哈希校验、干净目录验证等既有机制继续保留。库是否跟踪 lock 文件可以按包管理约定决定，但发布组合不能漂移。

安装器、代码签名、公证、升级回退和文件关联可以由平台打包层提供，不必塞入渲染内核。至少应形成一条真实应用的端到端发布模板，并明确 1.0 的 API 兼容范围与弃用政策。

**F10 · P2 · 跨平台实现、跨平台测试配置和跨平台验收需分别声明。**

SDL 层已提供文件拖放、MIME 剪贴板、显示器等包装，并有 `SdlEventPump` 支持多个底层窗口，不能把这些能力说成完全不存在。但 CUI DesktopApp 持有单个私有窗口并独占运行循环，尚未提供共享调度、多窗口状态、父子窗口和窗口间焦点的统一应用模型。

现有工作流配置了 Linux x86_64、macOS arm64 的托管无窗口任务，也配置了三个平台的交互式自托管 runner。这是验证基础设施；本次未读取远端任务运行结果，也没有对应平台实机，不能据此声称它们已通过。仓库当前只有 default 活动性能基线，不能将 Windows 基线套用到其它平台。

建议公开“可构建 / 基础运行 / 交互验收 / 可正式交付”四级平台矩阵，附版本与报告。各目标平台至少验证 IME、字体、系统对话框、混合 DPI/多显示器、快捷键、GPU 恢复和原生可访问性。CUI 多窗口能力在关闭协议成熟后再开展。

**F11 · P2 · 核心测试深度较好，但应用行为矩阵和长期成本证据不足。**

865 项测试全部通过的同时，本次仍能复现静止重绘、字符簇拆分和模态焦点问题，说明现有测试更擅长证明当前契约与内部一致性。增量/全量截图相同也可能是两条路径表现出同一语义问题。

建议将测试按“控件 × 输入方式 × 状态 × 平台”组织，明确未覆盖格子。每个可交互控件至少包含键盘、指针、禁用、焦点、无障碍、缩放和动态移除；容器补充极小尺寸、长内容、嵌套滚动和异常恢复；宿主补充静止、关闭确认和长时运行。

现有核心有局部命令内存、缓存预算和清理测试，应进一步增加整机 RSS/显存趋势、频繁开关窗口/弹层、文本与图片冷加载、长时间滚动和后台消息洪峰。本次没有发现足以要求整体重写内核的证据；模块较大或数量较多本身也不是缺陷，应以职责变化和调试成本决定拆分。

**建议的迭代顺序与退出条件**

以下按依赖关系排序，不作为在未知团队规模下的工期承诺。每轮均应保存反例、修复后补回归，并执行相应原有门禁。

| 迭代 | 主要交付 | 退出条件 |
|---|---|---|
| 第一轮：修复可复现问题 | Table 等值失效；统一默认文本移动/前向删除边界；Modal 焦点进入与恢复；常用控件默认语义 | 本报告探针转为正式回归；静止控件停止自发刷新；字符簇不被错误拆分；模态所有关闭路径恢复合理焦点；所列五类缺失控件有可操作语义 |
| 第二轮：补齐桌面应用契约 | 关闭确认；运行时主题和字号；可复现依赖及 L2 CI；表单状态与媒体失败反馈 | 未保存文档支持保存/放弃/取消；主题切换不丢业务状态或复用旧缓存；新环境复现同一依赖与质量检查 |
| 第三轮：支撑复杂业务 | 稳定 key 的表格数据接口、局部更新、树按需加载、编辑器中等规模优化 | 数据规模增长时稳定帧访问量不线性增长；插入/排序后选择和编辑状态跟随业务对象；大文本/图片有冷路径和内存预算 |
| 平台发布线：随目标市场推进 | 目标平台原生无障碍、交互 runner、签名打包与安装升级模板 | 每个宣称正式支持的平台有独立构建、真实输入、字体、无障碍、干净交付和性能证据 |
| 后续按需求扩展 | CUI 多窗口、原生菜单/托盘整合、打印、WebView、音视频、复杂图表 | 至少有真实应用驱动与明确维护边界；先验证语义、资源生命周期与端到端收益 |

建议把下一版本的验收指标从“控件总数、测试总数、最高 FPS”转向以下用户结果：

- 静止界面是否真正空闲；动画和输入是否能按时唤醒。
- 用户能否只用键盘或屏幕阅读器完成一条实际业务流程。
- 中文、组合字符、emoji 和 IME 的编辑结果是否符合预期。
- 文档关闭、保存失败和取消是否安全、可恢复。
- 10k/100k 数据局部变化是否只处理必要数据，选择与滚动身份是否稳定。
- 字号、主题和窗口大小变化后内容是否仍可达，状态与缓存是否一致。
- 同一发布版本能否在干净环境复现、安装、运行和升级。

**应用选型建议**

| 应用类型 | 当前建议 |
|---|---|
| Windows 内部工具、设置页、轻量看板、原型 | 可以采用；优先修复本报告 P1，并为真实工作流补测试 |
| 单窗口中等复杂业务应用 | 可以作为基础，需为表单、关闭确认、主题和复杂数据交互预留完善工作 |
| 对无障碍、国际化或 Linux/macOS 体验有明确交付承诺的公共软件 | 先建立目标平台验收与控件覆盖，暂不按“开箱完备”估算工作量 |
| IDE、专业文本编辑器、电子表格、复杂多窗口工作站 | 当前应视为需要继续建设的底座，不能按现有基础控件直接交付估算 |

最值得保护的资产是现有一致性内核、专用惰性容器和验证工具；最有价值的下一步，是让已展示的控件能力具备完整的编辑、焦点、无障碍、空闲和发布行为。
