# 字体与 Emoji 资源实测及优化

本轮扩展压力测试发现并修正了复合缓存键的 GC 失效；优化构建已完成 30 轮连续渲染流程。全量验收结果和可复现实验见文末。

本轮保留彩色 Emoji、连续字重、变量字体和已有文本接口，优化均在 CangjieSDL／CangjieGUI 仓颉代码中实现。继续使用官方 SDL_ttf 3.2.2，不引入 native 补丁、Qt 或 Skia 运行时依赖。Windows 本机最终 8 轮测量中，首次 Emoji 场景的进程私有内存从 **74.43 降至 66.62 MiB**；相对普通文本的额外占用从 **16.29 降至 8.33 MiB**，约减少 **49%**。

## 16.3 MiB 的来源

旧实现第一次绘制彩色字形时，既打开实际 Emoji 字体，又打开用于校准位图偏移的辅助字体。阶段采样分别增加约 7.3／7.8 MiB；按名称发现字体的开销很小，主要分配发生在原生字体打开时。普通 UI 也分配图集，不能把整个渲染器或图集都归入 Emoji 增量。

本机 `seguiemj.ttf` 为 12,450,664 字节，其中 COLR 表 7,133,988 字节（6.80 MiB）、CPAL 表 259,338 字节。官方 SDL_ttf 通过流打开字体；实际加载的 FreeType 2.13.2 会提取完整 COLR 表。这解释了为什么映射源文件并不自动消除原生字体的私有表副本。[SDL_ttf 3.2.2 源码](https://github.com/libsdl-org/SDL_ttf/blob/release-3.2.2/src/SDL_ttf.c)、[FreeType COLR 加载](https://github.com/freetype/freetype/blob/VER-2-13-2/src/sfnt/ttcolr.c)。

独立诊断程序对临时字体副本屏蔽 COLR 表入口，交错重复打开 10 轮：原文件打开增量中位数 7.586 MiB，诊断副本 0.766 MiB，差额 **6.820 MiB**。这是分配归因实验，受同进程分配器复用影响；生产实现没有删表、裁剪字体或降级颜色。独立 `TTF_CopyFont` 实验仍新增约 7.6 MiB。

因此，在当前字体和 SDL_ttf／FreeType 组合下，一份约 7～8 MiB 的原生彩色字体加载成本有实际依据，重复打开第二份则应避免。这不是所有平台、字体或 GUI 后端共同的理论最低内存。

## 成熟框架与官方 API 的启示

| 机制 | 查证结果与本轮决策 |
| --- | --- |
| Qt 字体资源复用 | QRawFont 使用隐式共享，QFont 匹配和原生字体对象应与每个控件的文字内容区分。本轮共享同 Renderer／同实际字号的不可变自动 Emoji 后备，保留主字体及显式后备连接隔离。[QRawFont](https://doc.qt.io/qt-6.10/qrawfont.html)、[QFont](https://doc.qt.io/qt-6/qfont.html)。 |
| Skia 字体缓存 | 字体身份与字号相关的缓存分开，并同时提供字节、数量预算及淘汰机制。本轮保留 24 配置上限，增加 64 MiB COLR／CPAL 表预算。[SkTypeface](https://api.skia.org/classSkTypeface.html)、[SkGraphics](https://api.skia.org/classSkGraphics.html)。 |
| SDL 无引擎文字对象 | `TTF_CreateText` 允许 engine 为 NULL；更新后可读取公开文字引擎操作。本轮移除仓颉文字引擎跨语言回调，以显式所有权管理布局与几何。[TTF_CreateText](https://wiki.libsdl.org/SDL3_ttf/TTF_CreateText)、[TTF_UpdateText](https://wiki.libsdl.org/SDL3_ttf/TTF_UpdateText)。 |
| SDL 字体复制 | `TTF_CopyFont` 共享文件，但不是共享完整解析后字体数据；本机实测不能消除 COLR 副本，未采用为内存方案。[TTF_CopyFont](https://wiki.libsdl.org/SDL3_ttf/TTF_CopyFont)。 |
| 动态改变字号 | `TTF_SetFontSize` 会使关联文字更新并清除已生成字形。不能在存活会话背后反复修改同一个字体来冒充不同字号，否则破坏布局稳定性。[TTF_SetFontSize](https://wiki.libsdl.org/SDL3_ttf/TTF_SetFontSize)。 |
| 公开字形接口 | 用 `TTF_GetGlyphImageForIndex` 取得实际位图，利用原字体小样本的公开绘制位置与 Surface 校准；只接受同字体、同 glyph ID、完整 alpha 像素一致的结果。失败仍走原 glyph-ID 校准，不读私有 TTF_Font／FT_Face。[字形图像 API](https://wiki.libsdl.org/SDL3_ttf/TTF_GetGlyphImageForIndex)。 |

另用 Qt 6.10.3 的 QImage／QPainter 在本机独立进程执行 8 轮相同文本测量和首次绘制。绘制准备完成后的私有内存增量：普通文本 3.31 MiB，含 Emoji 30.37 MiB；对应耗时 95.9／322.5 ms。实际字体为 Microsoft YaHei UI 和 Segoe UI Emoji。该实验包含 Qt 字体后端首次初始化，未包含整套窗口启动，不能与下面 CUI 的进程总量直接比较或据此排名。其作用是验证“成熟框架也有显著首次字体开销”，不是证明当前后端必然最佳。

## 实现及边界

- 自动 Emoji 后备按实际字号共享，只作为无后续连接的不可变叶子。租约保证缓存淘汰、reload 和存活测量会话互不破坏；不同字号不共用可变字体对象。
- 校准优先复用已打开字体。每个样本最多 128 UTF-8 字节，每字体最多 256 项／16 KiB；数值偏移最多 4096 项。SDL 回退分段时最多尝试 8 个 UTF-8 前缀，必须再次验证字形与像素，不改变应用 shaping 结果。
- 必须使用备用校准时，含至少 1 MiB 彩色表的辅助字体在本次绘制结束或失败时释放；小型辅助字体每处理 128 个新字形释放。数值偏移继续缓存。
- 虚拟流源文件校验和按元数据版本最多保留 512 项，只缓存数值；重开映射不再扫描整份文件，reload 后使用新版本。Windows 源键统一路径分隔符和 ASCII 大小写，面号、变量坐标仍参与区分。
- SFNT 目录只保存四字节数值标签，保留 ASCII、重复表及文件范围校验，避免重复保存和复制标签字符串。文字纹理键改为不可变对象；相等和哈希仍按字段值计算，原有跨帧／跨颜色缓存语义不变。CUI 段落缓存同步共享不可变键，避免 Map 与 LRU 节点重复保存复合值；新增等值键在 GC 后仍命中的回归。
- 彩色配置按原生字体去重统计 COLR／CPAL 表，超过 64 MiB 时淘汰最久未使用的彩色配置。它不是进程内存硬上限；当前请求、存活会话、其它表、原生字形和驱动另有开销。单个超预算请求保持可用。其它彩色格式仍受 24 配置数量限制，不能把 COLR 预算解释为跨格式完整内存统计。

压力试验复现了并发 GC 标记时的无效对象访问和 `latest->IsValidObject()` 校验失败。移除文字回调后的 10 轮初测通过，但扩大复测仍失败；尚未加入最新预算的隔离版本也会失败，排除了“释放更积极就是原因”的简单归因。调试器捕获了复合值键中失效的字符串引用；仅将表标签数值化仍不足，进一步改为不可变文字纹理键后，同一优化构建的 30 轮 × 207 组流程全部完成。新增长流程回归在对照版本中崩溃，在修正后通过。直接调用官方字体 API、单独的元数据／字典最小程序均通过，不能仅凭这些结果归责所有 SDL、FFI 或仓颉运行时操作。

进一步在对照源码中仅将纹理键由 struct 改为不可变 class，同一新增回归也恢复通过，保留了原先字体分配策略。该修正保留 `-O2`，没有通过关闭 GC、全局降低优化级别或增加强制 GC 来掩盖问题。测试同时覆盖字体样式使布局失效、拒绝提前关闭仍有布局的上下文和资源释放顺序。

## 最终性能

本机为 Intel Core Ultra 7 268V（8 核／8 线程）、Windows 11 Pro 26200、Cangjie 1.0.5、官方 SDL_ttf 3.2.2／FreeType 2.13.2，使用优化构建。各场景 8 轮、前后顺序交错，共 144 个独立进程；采用项目性能核亲和策略，测量期间不并行编译。不是重启机器后的冷磁盘测试。

“私有内存”为 Windows PrivateUsage，含仓颉运行时、原生字体、渲染缓存及驱动私有分配，不是 RSS、显存或字体独占内存。[指标定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)。耗时为墙钟时间，CPU 使用进程累计时间；CPU 计数约有 15.625 ms 量化，较小差值不能解释为明确回归或提升。

启动对照为本轮原始源码与最终源码。原始版长流程存在上述 GC 失败，因此工作负载对照采用**仅移除文字回调并修正纹理键、保留原字体分配／缓存策略**的 control 构建，隔离资源策略带来的变化。两类对照明确分开；本组 144 个测量进程全部完成，未从性能分布中剔除失败进程。此前阶段试验单独保留，不混入最终分布。

| 启动样本 | 私有内存，前 → 后 | 启动中位数，前 → 后 | 启动 MAD，前 → 后 |
| --- | ---: | ---: | ---: |
| 普通文本 | 58.14 → 58.29 MiB | 198.12 → 187.86 ms | 19.07 → 16.83 ms |
| 中文／Latin／🎉／👩🏽‍💻 | 74.43 → 66.62 MiB | 232.37 → 223.12 ms | 1.52 → 3.01 ms |

普通文本内存基本不变；其启动波动较大，不把约 10 ms 的中位数差解释为框架加速。Emoji 场景总私有内存减少 7.81 MiB，启动中位数减少 9.25 ms；CPU 中位数 242.19 → 218.75 ms，MAD 为 23.44／15.63 ms，仍不足以宣称确定的同幅 CPU 改善。

以下每进程 180 帧，每帧测量和绘制；暖帧取第 65 帧起的样本。32 配置场景为 **32 个指向相同 UI 字体的注册族别名**，用于隔离配置重复开销，不代表扫描 32 份字体文件。24 字号为 14～37 栅格像素循环；新增 Emoji 为 U+1F300 起 160 个不同码点循环。

| 工作负载 | 最终私有内存，control → 后 | 首帧，control → 后 | 暖帧中位数，control → 后 | 暖帧 P95，control → 后 |
| --- | ---: | ---: | ---: | ---: |
| 普通文本 | 59.69 → 58.70 MiB | 6.78 → 6.49 ms | 0.264 → 0.273 ms | 0.411 → 0.398 ms |
| 重复 Emoji 文本 | 75.51 → 66.49 MiB | 21.73 → 10.16 ms | 0.251 → 0.237 ms | 0.347 → 0.315 ms |
| 连续新增 Emoji | 81.28 → 73.03 MiB | 21.34 → 9.19 ms | 0.336 → 0.305 ms | 0.822 → 0.782 ms |
| 循环 32 个字体配置名 | 488.06 → 108.22 MiB | 21.72 → 10.08 ms | 9.271 → 1.086 ms | 10.899 → 1.775 ms |
| 循环 24 个字号 | 475.36 → 173.88 MiB | 21.78 → 9.45 ms | 0.329 → 4.922 ms | 0.451 → 6.480 ms |
| 重复斜体混排 | 75.31 → 65.59 MiB | 32.63 → 9.50 ms | 0.293 → 0.246 ms | 0.383 → 0.332 ms |
| 重复下划线混排 | 75.33 → 66.64 MiB | 21.98 → 10.50 ms | 0.253 → 0.254 ms | 0.347 → 0.341 ms |

180 帧进程 CPU 中位数依次为：普通文本 54.69 → 31.25 ms，重复 Emoji 46.88 → 39.06 ms，新增 Emoji 140.63 → 125.00 ms，32 配置 1796.88 → 250.00 ms，24 字号 273.44 → 992.19 ms，斜体 62.50 → 46.88 ms，下划线 46.88 → 31.25 ms。除配置轮换场景外，差值与计数粒度及噪声相近，不能据此宣称普遍的 CPU 降幅。

**24 字号是明确的内存／CPU 取舍。** 本机 Emoji 表预算约容纳 9 个字号；每帧换成缓存外字号必然重开字体，约增加 4.59 ms 暖帧时间，换来约 301 MiB 私有内存下降。阶段试验中，只做重复打开去重、尚未限制彩色表时，该场景约 267.72 MiB／0.240 ms。当前保留有界缓存，普通界面使用少量稳定字号；大量不同字号持续动画仍不适宜。不能把约 5 ms 的代价描述成所有输入或滚动都有。
